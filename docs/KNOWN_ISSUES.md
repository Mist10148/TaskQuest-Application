# Known issues and limitations

This list covers what remains after the 4.0 merge and the improvement pass that followed it (balance rework, new XP sources, shared lists and parties, per-user days, anti-cheat replay). Rows from earlier versions that were fixed have been removed; their numbers are not reused, so the numbering has gaps (a number is a stable name other documents refer to). The move from MySQL/TiDB to PostgreSQL ([MIGRATION_POSTGRES.md](MIGRATION_POSTGRES.md)) closed #27 (edited development migrations, now squashed into one baseline) and #48 (the legacy-upgrade collation risk), since MySQL, MariaDB and the legacy upgrade path are gone. The 29 bot issues and 13 web issues documented before 4.0 are resolved too; see [CHANGELOG.md](../CHANGELOG.md#400---2026-10-08) and [SECURITY.md](../SECURITY.md#3-vulnerabilities-fixed-in-40). Security-relevant residual risks are in [SECURITY.md](../SECURITY.md#known-residual-risks).

## Limitations

Things that are not as good as they could be, and what to do about them.

| # | Area | Issue | Impact | Workaround / plan |
|---|---|---|---|---|
| 2 | Economy | Lifetime XP for players from before 4.0 is reconstructed as max(balance, level floor). XP spent before 4.0 isn't counted. | Some veteran players' lifetime XP is lower than they actually earned. Levels never dropped. | None needed. Optionally backfill from `xp_transactions` if your history is complete. |
| 3 | Economy | `xp_spent` (spending achievements) is backfilled from class and skill purchases in `xp_transactions`; spending that predates the XP log is not counted. | A few veterans start below their true total. | None needed. |
| 5 | Bot | `/list` overviews are public messages; channel members can read list names and task names. | Information visible in channel. | Use `/list` in DMs. Mutations are owner-scoped. |
| 6 | Bot | The reorder selection (step 1 → step 2) is kept in memory. | A bot restart between the two selections asks you to start the reorder again. | Low impact. |
| 7 | Bot | Achievement pagination and class-browser position are kept in memory per user. | They reset after a restart. | Low impact. |
| 14 | Data | `xp_transactions` and `game_sessions` grow without bound. | Storage. | `npm run archive` moves old rows to archive tables ([DATABASE.md](DATABASE.md#backups-and-maintenance)); the Render blueprint schedules it weekly (`taskquest-archive`); on other hosts schedule it yourself. |
| 15 | Platform | Render background workers need a paid plan, and free web services sleep. | A free deployment of the bot disconnects when idle. | Use a paid worker, or another host. |
| 16 | Skills | `users.skill_points` is legacy and unused (skills cost XP). | — | Kept for compatibility; may be dropped in a future migration. |
| 17 | AI | The AI service's SQL runs against PostgreSQL with pgvector in CI (`tests/postgres`), but nothing has run against real Gemini yet, and the default Gemini model ids may need updating. | A first live run may need small fixes (model ids, structured-output or safety-filter quirks). | Follow the [live-run checklist](OPERATIONS.md#first-live-gemini-run) with a staging key before enabling for users. |
| 18 | AI | The eval suites in `apps/ai/tests/evals` have only been run offline with fake models, and the golden sets are still small (50 retrieval queries, 6 summary and 6 prioritizer cases). | Retrieval and summary quality against real Gemini is unmeasured. | Run the live evals with a staging key ([OPERATIONS.md](OPERATIONS.md#first-live-gemini-run)) and grow the golden sets from real (anonymised) data. |
| 20 | AI | The vector cache and the prioritizer result cache live in process memory. | With several AI instances each warms its own cache. | Fine on one instance; use a shared cache or vector store if scaled out. |
| 21 | Bot | The @mention chat cooldown (3 s per user) is kept in memory. | It resets after a restart. | Low impact; the daily AI quota still applies. |
| 22 | AI | Without the Message Content intent, the bot cannot read replies to it that have the ping turned off. | Those replies are ignored. | Mention the bot, keep the reply ping on, or enable `AI_CHAT_MESSAGE_CONTENT` with the intent. |
| 24 | Web | A Playwright smoke suite covers the main flows (`npm run test:e2e`), the pure logic has unit tests, and component tests (jsdom + Testing Library) cover the quick-add bar, the task row and board, the calendar, the bottom nav, the assistant's confirmation card, the reward breakdown, the shared loading/error states, the XP bar, stat card, achievement badge, the quests card and the Review page. Many components (the Games page, the Skills and Classes pages, dialogs) still have no tests. | Rendering details of an untested component can regress without a failing test. | Grow the component tests with new work. |
| 26 | Docs | The README has no screenshots, and the pages added in the improvement pass (Stats, Review, Focus, Shop, Party) are documented in text only. | — | Needs a signed-in session to capture; add them from a real deployment. |
| 30 | Web push | Push needs HTTPS (or `localhost`), the three `WEB_PUSH_*` VAPID variables on the web server and `WEB_PUSH_INTERNAL_URL` on the bot, and each browser must opt in under Settings. Only the browsers' own push services are accepted as endpoints. Delivery has not been exercised against real push services in this repository. | Reminders reach the browser only when all of that is set; otherwise only the Discord DM is sent. | Follow [DEPLOYMENT.md](DEPLOYMENT.md#web-push-optional). Push for AI results is not built. |
| 31 | AI | The daily AI quota (`AI_DAILY_REQUEST_LIMIT`) resets at 00:00 UTC for everyone, not at the user's local midnight. | A user in a far time zone can find the quota used up early in their day. | Raise the limit if it is too tight. |
| 35 | Sharing | Invitation probing is reduced but not impossible: every call answers one neutral message and the confirmation step shows a name only for someone who can be invited, but a manager's own pending-invitations list still shows which invitations were really created, and the preview shows the display name for an exact username. Invitees must have used TaskQuest since the upgrade (their handle is stored at login). | A patient inviter can learn whether a specific username can be invited. | Accepted and bounded by rate limits (30 sends a day) and the per-person `accept_invites` switch. See [SECURITY](../SECURITY.md#known-residual-risks). |
| 39 | Games | Arcade hardening options B (calibrated caps, per-run minimum duration, per-account cooldown, `game_reward` off the weekly board) and C (signed checkpoints) were not built after input replay shipped. | A scripted solver still counts on the weekly board. | Optional. See [arcade-anti-cheat](design/arcade-anti-cheat.md). |
| 40 | Bot | A reminder DM that was sent but whose "sent" mark then fails to save is repeated at the next run. A failure no longer stops the rest of the batch. | Rare duplicate reminder after a database error. | Accepted: sending first is the safer failure. |
| 44 | Bot | The streak warning is a DM (and a web push when set up) once a day from 18:00 in the player's zone, only for players with reminders and XP on; the bot's class browser has no skill reset. | A player with closed DMs and no push gets no warning (the Today page still shows it). | Turn on web push, or open the Today page. |
| 45 | Data | Archived XP is not part of stats charts that look back further than the days you keep, and the weekly Render job (`taskquest-archive`, `--days 365`) is part of the blueprint only: other hosts must schedule `npm run archive` themselves. | Stats looking back more than a year miss archived XP; on a host without the job the log keeps growing. | Keep the window at a year or more, and schedule the job (cron, a Render job) elsewhere. |
| 47 | Sharing | Handing a list over checks the new owner's list and task limits under the list lock but does not lock the new owner's account (that would reverse the lock order used when tasks are added and risk a deadlock). | If the new owner adds tasks at the very moment of the hand-over, they can end slightly over the 5,000 task limit; later adds are then refused. | Low impact; retry or remove tasks. |

## By design

Things that look like gaps but are decisions, with the reason.

| # | Area | Issue | Impact | Workaround / plan |
|---|---|---|---|---|
| 1 | Games | Arcade runs are verified by replaying the recorded inputs on the server, so a score cannot be edited. A script that solves a game offline can still submit a perfect, valid recording. | A scripted client can earn up to the free-game cap (500 XP per day) with plausible runs. | Bounded by the per-run payout, the 3 s cooldown and the daily cap, not detected. Design: [arcade anti-cheat](design/arcade-anti-cheat.md). |
| 10 | Tasks | A repeating task creates its next copy when it is completed. If you never complete it, nothing is created, and skipped periods are not back-filled. | A habit you skip for a month doesn't pile up. | By design. |
| 11 | Tasks | Subtasks nest one level deep, and an import keeps the links only for subtasks whose parent is in the same file. | — | By design. |
| 13 | Calendar | The calendar feed address is a bearer secret in a URL: anyone who has it can see your deadlines. | A leaked address exposes list and task names with dates. | Rotate or turn it off in Settings; the old address stops working at once. |
| 28 | Economy | The level curve is linear (100 lifetime XP per level), so levels come quickly late in the game and the level-based class effects (Wizard Wisdom, Tank cap, Archer hit chance) rise with it until their caps (Wisdom stops at 50, level 25; the Tank cap at level 30; the Archer at 97%). A steeper curve was rejected so that no veteran's level drops. | Level 30 (the prestige threshold) needs 2,900 lifetime XP. | Prestige and the cosmetic shop are the late-game sinks. Rationale: [design/balance.md](design/balance.md). |
| 29 | Parties | The party target counts only members who finished at least 6 tasks themselves this week and only completions since each member joined, so the target moves while the week runs (up to 12 per active member), and the owner can remove a member. Rewards need 6 tasks of your own. | A party's goal can look different from one day to the next, and a reward is lost to a member who is removed before claiming. | By design: it stops a spare account or one strong member carrying the party. See [GAMEPLAY](GAMEPLAY.md#5h-parties). |
| 32 | Data | A template keeps each task's name, description, priority, tags and repeat, but not subtasks (they become plain tasks), due dates or completion. Templates are personal (up to 20 of up to 30 tasks). | A template of a project plan does not carry its dates or hierarchy. | By design. Set dates after applying it. |
| 33 | Bot | Discord select menus hold 25 options, so long lists and task lists are paged (`◀ Previous` / `▶ More`) and search results show `(showing 25 of N)` without paging. (Browser positions kept in memory are #6 and #7.) | With hundreds of tasks the Discord editor is slower than the web app. | Narrow the search, or use the web app for large lists. |
| 34 | Sharing | The owner can hand a shared list to one of its members (Members dialog, `POST /api/lists/:id/transfer`), but shared lists are not part of exports, templates, the AI assistant or auto-delete, and a list cannot be handed to someone who is not a member. | If the owner stops using TaskQuest without handing the list over, its members cannot take it over. | Ask the owner to hand it over, or copy the tasks into a quest you own. |
| 36 | Time | A time zone change is allowed once every 24 hours, so hopping between zones can still open one extra capped day now and then (about 70 XP a day at most). Weekly, monthly and daily quest claims and the weekly review are checked against the real time of the last claim, so a zone change cannot pay them twice. The weekly leaderboard and the party quest use one global UTC week for everybody. | Players in some time zones see their weekly board or party week start at an odd local hour. | By design: a shared board needs one week. |
| 37 | Gameplay | The daily streak continues by calendar day (your time zone) but the claim cooldown is a rolling 24 hours, and the streak leaderboard still uses the equivalent rolling 48/72/96 hour windows. | The leaderboard can show a lapsed streak for up to a day after it ended; a claim just before midnight can be followed by one just after. | By design: it is a display approximation, the claim itself is exact. |
| 41 | Skills | Resetting a skill tree (web and API only, not the bot) refunds 75% and is limited to once a day; the refund never counts as lifetime XP. | A mistaken purchase costs 25% of that tree. | By design: a full refund would make every skill free to try. |
| 42 | Previews | The "what would I earn?" numbers are a simulation of a 10 XP task, five a day on a 7 day streak, in the situation each class is built for (a plain task for the others); a percentage boost rounds down on a small reward, as in the game. | A preview is an estimate of your average, not of any single task. | Compare with `npm run xp-report` once there is history. |
| 43 | Bonuses | The good-estimate bonus pairs a task with the focus session that ended within 10 minutes before it was finished; it cannot know which task the session was for. Party assist pays for any completion while in a party of two or more. Both are capped (30 and 15 XP a day). | A player can set an estimate to match a session they just ran. | Bounded by the daily caps. |
