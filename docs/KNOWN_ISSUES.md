# Known issues and limitations

This list covers what remains after the 4.0 merge and the improvement pass that followed it (balance rework, new XP sources, shared lists and parties, per-user days, anti-cheat replay). Rows from earlier versions that were fixed have been removed; their numbers are not reused, so the numbering has gaps (a number is a stable name other documents refer to). The move from MySQL/TiDB to PostgreSQL ([MIGRATION_POSTGRES.md](MIGRATION_POSTGRES.md)) closed #27 (edited development migrations, now squashed into one baseline) and #48 (the legacy-upgrade collation risk), since MySQL, MariaDB and the legacy upgrade path are gone. The 29 bot issues and 13 web issues documented before 4.0 are resolved too; see [CHANGELOG.md](../CHANGELOG.md#400---2026-10-08) and [SECURITY.md](../SECURITY.md#3-vulnerabilities-fixed-in-40). The October 2026 follow-up pass closed #6, #7 (the bot's browsers no longer keep state in memory), #16 (`users.skill_points` dropped), #20 (shared prioritizer cache), #31 (AI quota at the user's midnight) and #46 (the three red API tests), and narrowed #39, #40, #44 and #47; each is described in the [CHANGELOG](../CHANGELOG.md#unreleased). Security-relevant residual risks are in [SECURITY.md](../SECURITY.md#known-residual-risks).

## Limitations

Things that are not as good as they could be, and what to do about them.

| # | Area | Issue | Impact | Workaround / plan |
|---|---|---|---|---|
| 2 | Economy | Lifetime XP for players from before 4.0 is reconstructed as max(balance, level floor). XP spent before 4.0 isn't counted. | Some veteran players' lifetime XP is lower than they actually earned. Levels never dropped. | None needed. Optionally backfill from `xp_transactions` if your history is complete. |
| 3 | Economy | `xp_spent` (spending achievements) is backfilled from class and skill purchases in `xp_transactions`; spending that predates the XP log is not counted. | A few veterans start below their true total. | None needed. |
| 5 | Bot | `/list` overviews are public messages; channel members can read list names and task names. | Information visible in channel. | Use `/list` in DMs. Mutations are owner-scoped. |
| 14 | Data | `xp_transactions`, `game_sessions` and `item_activity` grow without bound. | Storage. | `npm run archive` moves old XP and game rows to archive tables and deletes old task history ([DATABASE.md](DATABASE.md#backups-and-maintenance)); the Render blueprint schedules it weekly (`taskquest-archive`); on other hosts schedule it yourself. |
| 15 | Platform | Render background workers need a paid plan, and free web services sleep. | A free deployment of the bot disconnects when idle. | Use a paid worker, or another host. |
| 17 | AI | The AI service's SQL runs against PostgreSQL with pgvector in CI (`tests/postgres`), but nothing has run against real Gemini yet, and the default Gemini model ids may need updating. | A first live run may need small fixes (model ids, structured-output or safety-filter quirks). | Run `python -m app.preflight --check-models` (it asks Google which of the configured ids exist and can do the job), then follow the [live-run checklist](OPERATIONS.md#first-live-gemini-run) with a staging key before enabling for users. |
| 18 | AI | The eval suites in `apps/ai/tests/evals` have only been run offline with fake models, and the golden sets are still small (70 retrieval queries, 10 summary and 10 prioritizer cases). | Retrieval and summary quality against real Gemini is unmeasured. | Run the live evals with a staging key ([OPERATIONS.md](OPERATIONS.md#first-live-gemini-run)), judge the report with `python -m tests.evals.compare`, and grow the golden sets from real (anonymised) data. |
| 22 | AI | Without the Message Content intent, the bot cannot read replies to it that have the ping turned off. | Those replies are ignored. | Mention the bot, keep the reply ping on, or enable `AI_CHAT_MESSAGE_CONTENT` with the intent. |
| 24 | Web | A Playwright smoke suite covers the main flows (`npm run test:e2e`), the pure logic has unit tests, and component tests (jsdom + Testing Library) cover the quick-add bar, the task row and board, the calendar, the bottom nav, the assistant's confirmation card, the reward breakdown, the shared loading/error states, the XP bar, stat card, achievement badge, the quests card, the Review page, the task detail drawer, the bulk-edit dialog, the command palette and the welcome tour. Many components (the Games page, the Skills and Classes pages, dialogs) still have no tests. | Rendering details of an untested component can regress without a failing test. | Grow the component tests with new work. |
| 26 | Docs | The README has no screenshots, and the pages added in the improvement pass (Stats, Review, Focus, Shop, Party) are documented in text only. | — | An opt-in Playwright spec captures twelve pages from the seeded e2e app (`CAPTURE_SCREENSHOTS=1 npm run e2e -w @taskquest/web -- screenshots`, [CONTRIBUTING](../CONTRIBUTING.md#readme-screenshots)); the images still have to be captured, checked and committed. |
| 30 | Web push | Push needs HTTPS (or `localhost`), the three `WEB_PUSH_*` VAPID variables on the web server and `WEB_PUSH_INTERNAL_URL` on the bot, and each browser must opt in under Settings. Only the browsers' own push services are accepted as endpoints. Delivery has not been exercised against real push services in this repository. | Reminders reach the browser only when all of that is set; otherwise only the Discord DM is sent. | Follow [DEPLOYMENT.md](DEPLOYMENT.md#web-push-optional). AI results use push in two narrow ways only (the Monday recap, and a local notice for a slow summary or ranking when you left the tab); a server push for every AI reply is not built, because the answer already reaches the open page. |
| 35 | Sharing | Invitation probing is reduced but not impossible: every call answers one neutral message and the confirmation step shows a name only for someone who can be invited, but a manager's own pending-invitations list still shows which invitations were really created, and the preview shows the display name for an exact username. Invitees must have used TaskQuest since the upgrade (their handle is stored at login). | A patient inviter can learn whether a specific username can be invited. | Accepted and bounded by rate limits (30 invitations a day, and 100 lookups a day per account and 300 per address, on top of the 15 minute limits) and the per-person `accept_invites` switch. See [SECURITY](../SECURITY.md#known-residual-risks). |
| 39 | Games | Arcade hardening option B is partly built: free-game XP is off the public weekly board, a run shorter than 5 seconds of play pays nothing, and `npm run arcade-report` shows how fast real players score so the plausibility bound can be calibrated. Not built: tighter bounds (there is no real play data yet, and a bound that rejects an honest player cancels their run), a per-game cooldown (the shared 3 s cooldown and the daily cap already bound it, and it would only add friction for quick retries) and option C (signed checkpoints). | A scripted solver can still earn the daily free-game cap, but it can no longer rank on the weekly board. | Run `npm run arcade-report` once there are real runs; lower `maxPointsPerSecond` only where the headroom is large. See [arcade-anti-cheat](design/arcade-anti-cheat.md). |
| 40 | Bot | A reminder DM that was sent but whose "sent" mark keeps failing to save (three tries, 50 ms and 100 ms apart) is repeated at the next run. A failure no longer stops the rest of the batch. | A duplicate reminder only when the database stays down for the whole retry window. | Accepted: sending first is the safer failure, and the retry removes the one-off errors. |
| 44 | Bot | The streak warning is a DM (and a web push when set up) once a day from 18:00 in the player's zone, only for players with reminders and XP on. | A player with closed DMs and no push gets no warning (the Today page still shows it). | Turn on web push, or open the Today page. |
| 45 | Data | Archived XP is not part of stats charts that look back further than the days you keep, and the weekly Render job (`taskquest-archive`, `--days 365`) is part of the blueprint only: other hosts must schedule `npm run archive` themselves. | Stats looking back more than a year miss archived XP; on a host without the job the log keeps growing. | Keep the window at a year or more, and schedule the job (cron, a Render job) elsewhere. |
| 47 | Sharing | A hand-over locks the new owner's account before the list (user row, then list: the order every writer uses), so the new owner's own adds cannot slip past the limit during it. Adding a task takes only the actor's account and the list, not the list owner's, so a *member* adding to another quest the new owner owns at the very same moment is not held back. | In that narrow race the new owner can end slightly over the 5,000 task limit; later adds are then refused. | Low impact; retry or remove tasks. Closing it would mean locking the list owner's account on every add to a shared list. |
| 49 | Quests | Auto-delete (on by default) removes a finished list 5 days after its last task is done, and quests, the weekly review, the weekly goal and party progress are counted live from list and task rows. Deleting a list therefore removes its tasks from those counts. | A player who finishes many tasks in one list early in the week can lose some of that progress towards a weekly or monthly quest or goal if the list is auto-deleted before the period ends. | Turn auto-delete off in Settings, or claim before the list is cleaned up. Fixing it is a product decision (delay the delete, or keep a progress counter that deletes do not touch). |
| 50 | Parties | A party of one person can claim both party rewards (12 tasks, 60 focus minutes), because the target is `12 x max(1, active members)`. | A solo player earns up to 100 XP a week from it. | Possibly intended; decide whether a claim should need two members. |
| 51 | AI | `/ask` creates a new chat thread each time, checkpoints and idle threads are never pruned, `/internal/index` is called on every edit with no debounce (the `embed` feature is not metered), and the "double Approve runs once" lock is per process, so with several AI instances two clicks can reach two instances. | Table growth, extra embedding calls and, in a multi-instance deployment only, a confirmed write that could run twice. | Run one AI instance until a database lock or a thread-row claim replaces the in-process lock; prune old rows by hand. |
| 52 | Bot | Reminder DMs are sent before they are marked, and the job guard is per process, so two bot replicas (or a deploy overlap) can send the same reminder twice. `/list`, `/profile`, the class shop and achievements reply without deferring, so a slow database round trip could miss Discord's 3 second window. | A duplicate reminder in a multi-replica or overlapping deploy; rarely, "The application did not respond". | Run one bot worker (the blueprint does). |
| 53 | Web | There is no offline write queue: a change made while offline is refused with a plain message. (The other rough edges from the October review, the restarting tour, one toast per bulk completion, the quest not being in the URL and the reorder flicker, are fixed; see the [CHANGELOG](../CHANGELOG.md#unreleased).) | No offline editing. | Deliberate for now: rewards are decided by the server, so a queue would need conflict rules. See the roadmap in [PRD §11](PRD.md#11-roadmap). |
| 57 | Security | The rate limiters (login, AI, and the 24-hour invitation caps behind #35) keep their counters in memory. | A restart or deploy resets them, and each instance counts alone; a sleeping free web service forgets them often. | Run one instance and expect resets, or move the counters to a shared store (see the [ROADMAP](ROADMAP.md)). |
| 58 | Security | One token (`AI_INTERNAL_TOKEN`) protects `/internal/*` and is also the fallback for the push token. `/internal` trusts the Discord ID in the body, so anything holding the token can act as any user. | The bot and the AI service share one trust level. | Keep the token in the private env group only; splitting it into narrower tokens is on the [ROADMAP](ROADMAP.md). |
| 59 | Performance | Weekly and streak leaderboards compute a score per player with a correlated subquery, and the caches are per process (requests that arrive while a board is being computed share that one query). | Each instance computes every board it is asked for, and `/api/leaderboard/me` can ask for 72 board and class combinations. | A shared cached board is planned. |
| 60 | Performance | `GET /api/lists/:id`, the calendar feed and the AI service's per-user item load return everything, up to the 5,000 task limit. | Large quests are slow to load. | Archive or split very large quests; limit and cursor parameters are on the [ROADMAP](ROADMAP.md). |
| 61 | Security | The calendar feed token is stored in plain text, because it is a bearer secret in a URL. | A database reader can subscribe to a user's feed. | Regenerate it from Settings if exposed; hashing it is possible later. |
| 62 | Data | The migration runner records applied migrations by name only (no checksums), and `001_baseline` needs the `vector` extension even with AI off. | An edited migration that already ran is not noticed; plain Postgres without pgvector cannot start. | Never edit a shipped migration; use the pgvector image (`npm run db:up`). |

## By design

Things that look like gaps but are decisions, with the reason.

| # | Area | Issue | Impact | Workaround / plan |
|---|---|---|---|---|
| 1 | Games | Arcade runs are verified by replaying the recorded inputs on the server, so a score cannot be edited. A script that solves a game offline can still submit a perfect, valid recording. | A scripted client can earn up to the free-game cap (500 XP per day) with plausible runs, but not rank on the weekly board with it. | Bounded by the per-run payout, the 5 second minimum, the 3 s cooldown and the daily cap, not detected. Design: [arcade anti-cheat](design/arcade-anti-cheat.md). |
| 10 | Tasks | A repeating task creates its next copy when it is completed. If you never complete it, nothing is created, and skipped periods are not back-filled. | A habit you skip for a month doesn't pile up. | By design. |
| 11 | Tasks | Subtasks nest one level deep, and an import keeps the links only for subtasks whose parent is in the same file. | — | By design. |
| 13 | Calendar | The calendar feed address is a bearer secret in a URL: anyone who has it can see your deadlines. | A leaked address exposes list and task names with dates. | Rotate or turn it off in Settings; the old address stops working at once. |
| 28 | Economy | The level curve is linear (100 lifetime XP per level), so levels come quickly late in the game and the level-based class effects (Wizard Wisdom, Tank cap, Archer hit chance) rise with it until their caps (Wisdom stops at 50, level 25; the Tank cap at level 30; the Archer at 97%). A steeper curve was rejected so that no veteran's level drops. | Level 30 (the prestige threshold) needs 2,900 lifetime XP. | Prestige and the cosmetic shop are the late-game sinks. Rationale: [design/balance.md](design/balance.md). |
| 29 | Parties | The party target counts only members who finished at least 6 tasks themselves this week and only completions since each member joined, so the target moves while the week runs (up to 12 per active member), and the owner can remove a member. Rewards need 6 tasks of your own. | A party's goal can look different from one day to the next, and a reward is lost to a member who is removed before claiming. | By design: it stops a spare account or one strong member carrying the party. See [GAMEPLAY](GAMEPLAY.md#5i-parties). |
| 32 | Data | A template keeps each task's name, description, priority, tags and repeat, but not subtasks (they become plain tasks), due dates or completion. Templates are personal (up to 20 of up to 30 tasks). | A template of a project plan does not carry its dates or hierarchy. | By design. Set dates after applying it. |
| 21 | Bot | The @mention chat cooldown (3 s per user) is kept in memory, and resets with a restart. | A user can send one message right after a restart without waiting. | By design: a 3 second cooldown is not worth a database round trip per mention; the daily AI quota (in the database) still applies. The reorder, achievement and class-browser positions used to be in memory too; they now travel in the buttons' custom IDs. |
| 33 | Bot | Discord select menus hold 25 options, so long lists and task lists are paged (`◀ Previous` / `▶ More`) and search results show `(showing 25 of N)` without paging. | With hundreds of tasks the Discord editor is slower than the web app. | Narrow the search, or use the web app for large lists. |
| 34 | Sharing | The owner can hand a shared list to one of its members (Members dialog, `POST /api/lists/:id/transfer`), but shared lists are not part of exports, templates, the AI assistant or auto-delete, and a list cannot be handed to someone who is not a member. | If the owner stops using TaskQuest without handing the list over, its members cannot take it over. | Ask the owner to hand it over, or copy the tasks into a quest you own. |
| 36 | Time | A time zone change is allowed once every 24 hours, so hopping between zones can still open one extra capped day now and then (about 70 XP a day at most). Weekly, monthly and daily quest claims and the weekly review are checked against the real time of the last claim, so a zone change cannot pay them twice. The weekly leaderboard and the party quest use one global UTC week for everybody. | Players in some time zones see their weekly board or party week start at an odd local hour. | By design: a shared board needs one week. |
| 37 | Gameplay | The daily streak continues by calendar day (your time zone) but the claim cooldown is a rolling 24 hours, and the streak leaderboard still uses the equivalent rolling 48/72/96 hour windows. | The leaderboard can show a lapsed streak for up to a day after it ended; a claim just before midnight can be followed by one just after. | By design: it is a display approximation, the claim itself is exact. |
| 41 | Skills | Resetting a skill tree (web and API only, not the bot) refunds 75% and is limited to once a day; the refund never counts as lifetime XP. | A mistaken purchase costs 25% of that tree. | By design: a full refund would make every skill free to try. |
| 42 | Previews | The "what would I earn?" numbers are a simulation of a 10 XP task, five a day on a 7 day streak, in the situation each class is built for (a plain task for the others); a percentage boost rounds down on a small reward, as in the game. | A preview is an estimate of your average, not of any single task. | Compare with `npm run xp-report` once there is history. |
| 43 | Bonuses | The good-estimate bonus pairs a task with the focus session that ended within 10 minutes before it was finished; it cannot know which task the session was for. Party assist pays for any completion while in a party of two or more. Both are capped (30 and 15 XP a day). | A player can set an estimate to match a session they just ran. | Bounded by the daily caps. |
| 54 | Tasks | A quest that takes in an already finished task by a move (`POST /api/items/:id/move`) counts as cleared from then on and never pays the list-cleared bonus, even if most of its tasks are finished there later. Moving the last open task out of a quest leaves only finished tasks behind, so auto-delete can remove it 5 days after its last change. | A player who tidies finished tasks into a project quest loses that quest's 25 XP clear bonus. | By design: otherwise moving finished tasks into a fresh quest would clear it with one new task. Move tasks before finishing them, or turn auto-delete off. |
| 55 | Tasks | Task history has no `created` entry for tasks added in bulk (a JSON or CSV import, a template applied, the AI service's create-list tool) or for the next copy of a repeating task, and description, tag, repeat, estimate and order changes are not recorded. Entries older than the archive window are deleted. | The history of such a task starts at its first recorded change. | Deliberate: one import must not write thousands of rows. Add a kind (and a CHECK value) in a new migration if more is needed. |
| 56 | Tasks | Comments have no per-task cap and no editing (delete and post again); posting is limited to 30 a minute per account, a thread shows its latest 200, and the export carries the comments you wrote but an import does not bring them back. | A long-running task can collect many comments. | Bounded by the rate limit; add a cap if a real thread grows too long. |
