# Moving from MySQL/TiDB to PostgreSQL (Supabase)

This page explains why and how TaskQuest moved its database from MySQL (TiDB Cloud in production, MySQL/MariaDB locally) to PostgreSQL hosted on Supabase. It is the reference for the code changes and the runbook for the cutover.

## Decisions

| Question | Decision |
|---|---|
| Data | **Start fresh.** The Supabase database starts empty; no rows are copied from TiDB. Players link again through the bot or the web login. |
| Dialects | **PostgreSQL only.** MySQL and MariaDB support is removed: one SQL dialect, one test matrix. |
| Migrations | **Squashed.** The 26 MySQL migrations are replaced by one Postgres baseline, `001_baseline`, which creates the final schema. The old files stay in git history. New migrations continue from `002` (`002` to `006` exist now, so the next one is `007`). |
| Supabase features | **Plain Postgres + pgvector.** No Supabase Auth, no Row Level Security, no client-side Supabase SDK. The apps connect with an ordinary Postgres connection string. AI embeddings move to a `vector(768)` column. |

## What changes

| Area | Before | After |
|---|---|---|
| Node driver (`packages/shared`, `apps/server`) | `mysql2` | `pg` (node-postgres), behind a small compatibility layer in `packages/shared/src/db/pool.js` |
| Python driver (`apps/ai`) | SQLAlchemy + `aiomysql` / `PyMySQL` | SQLAlchemy + `asyncpg`, with codecs that keep naive-UTC datetimes and ISO date strings working (`apps/ai/app/db/pool.py`) |
| Schema | 26 MySQL migrations | `001_baseline` in Postgres DDL |
| Migration lock | `GET_LOCK('taskquest_migrations')` | `pg_try_advisory_lock` (session level; a second process waits and retries) |
| RAG search | BLOB embeddings, cosine similarity in numpy | `vector(768)` column, exact `ORDER BY embedding <=> :q` in SQL over the user's rows (numpy stays for the SQLite tests) |
| CI services | `mysql:8.0` | `pgvector/pgvector:pg16` |
| Backups | `mysqldump` | Supabase daily backups plus `pg_dump` |

### The compatibility layer

There are about 740 queries in the Node code. To keep the change reviewable, the call sites keep their shape:

- **Placeholders.** Queries still use `?` placeholders. The layer rewrites them to `$1, $2, …`, skipping quoted strings, quoted identifiers and comments.
- **Return values.** `conn.query()` and `pool.query()` still resolve to `[rows, fields]`.
- **Write results.** For `INSERT` / `UPDATE` / `DELETE`, `rows` is a result header `{ affectedRows, insertId, rows }`, with or without a `RETURNING` clause:
  - `affectedRows` is the Postgres `rowCount`.
  - `insertId` is the `id` of the first returned row. So an insert that needs the new id adds `RETURNING id` and reads `[{ insertId }]` as before.
- **Booleans.** Boolean parameters are sent as `1` / `0`, because flag columns are `SMALLINT` (see below).
- **Transactions.** `getConnection()`, `beginTransaction()`, `commit()`, `rollback()`, `release()` and `ping()` keep working. `withTransaction()` retries on Postgres deadlocks (`40P01`) and serialization failures (`40001`).

## Type mapping

| MySQL | PostgreSQL | Notes |
|---|---|---|
| `INT AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | `BIGINT AUTO_INCREMENT` becomes `BIGINT … IDENTITY` |
| `BOOLEAN` / `TINYINT(1)` | `SMALLINT` | The code compares flags with `= 1` / `= 0` and reads them as numbers, so they stay numeric |
| `TINYINT UNSIGNED` | `SMALLINT` | |
| `INT UNSIGNED` | `BIGINT` | `web_sessions.expires` |
| `ENUM(…)` | `VARCHAR` + `CHECK (col IN (…))` | A CHECK is easier to change than a Postgres enum type |
| `JSON` | `JSONB` | |
| `BLOB` / `LONGBLOB` | `BYTEA` | Checkpoints |
| `BLOB` (embeddings) | `vector(768)` | Needs the `vector` extension |
| `TEXT` / `MEDIUMTEXT` | `TEXT` | |
| `CHAR(n)` | `VARCHAR(n)` | Avoids Postgres blank padding |
| `DATETIME` / `TIMESTAMP` (any precision) | `TIMESTAMPTZ(3)` | Millisecond precision, like a JavaScript `Date`, so a stored time reads back exactly; every session runs in UTC |
| `DATE` | `DATE` | Still returned to JavaScript as a `'YYYY-MM-DD'` string |
| `utf8mb4_unicode_ci` names that must be unique ignoring case | `CITEXT` | `lists.name`, `task_templates.name`, `parties.name` |
| `utf8mb4_bin` | `VARCHAR` / `TEXT` | Postgres text comparison is already exact |
| `ON UPDATE CURRENT_TIMESTAMP` | *(removed)* | Updates set `updated_at = CURRENT_TIMESTAMP` themselves (see below) |
| `CREATE TABLE … LIKE` | explicit `CREATE TABLE` | The archive tables |

## SQL rewrite rules

| MySQL | PostgreSQL |
|---|---|
| `` `name` `` | `name`, or `"name"` for a reserved word |
| `INSERT IGNORE INTO t …` | `INSERT INTO t … ON CONFLICT DO NOTHING` |
| `ON DUPLICATE KEY UPDATE a = VALUES(a)` | `ON CONFLICT (<unique key>) DO UPDATE SET a = EXCLUDED.a` |
| `result.insertId` | add `RETURNING id` |
| `UTC_TIMESTAMP()`, `NOW()` | `CURRENT_TIMESTAMP` |
| `UTC_DATE()`, `CURDATE()` | `CURRENT_DATE` (the session is UTC) |
| `x - INTERVAL ? DAY` | `x - make_interval(days => ?)` |
| `IF(c, a, b)` | `CASE WHEN c THEN a ELSE b END` |
| `TIMESTAMPDIFF(MICROSECOND, a, b) DIV 1000` | `FLOOR(EXTRACT(EPOCH FROM (b - a)) * 1000)` |
| `UNIX_TIMESTAMP(c)` | `EXTRACT(EPOCH FROM c)` |
| `a DIV b` | `FLOOR(a / b)` or integer `/` |
| `col IN (?)` with an array | `col = ANY(?)` |
| `LIKE` (case-insensitive under MySQL collation) | `ILIKE` |
| `SUM(a = b)` | `COUNT(*) FILTER (WHERE a = b)` or `SUM(CASE … END)` |
| `UPDATE a JOIN b … SET` | `UPDATE a SET … FROM b WHERE …` |
| `GET_LOCK` / `RELEASE_LOCK` | `pg_advisory_lock` / `pg_advisory_unlock` |
| error `ER_DUP_ENTRY` | SQLSTATE `23505` (`isUniqueViolation(err)`) |
| error `ER_LOCK_DEADLOCK` | SQLSTATE `40P01` |
| error `ER_NO_SUCH_TABLE` | SQLSTATE `42P01` |

`updated_at` pinning (`SET updated_at = updated_at`, the MySQL way to stop `ON UPDATE CURRENT_TIMESTAMP` firing) is gone. Postgres has no implicit update stamp, so the queries that should bump `updated_at` set it explicitly:
- items, lists and ai_chat_threads edits;
- ai_embeddings re-indexing (the AI service already did this).

Bookkeeping writes leave it alone: reminder flags, XP flags and quest facts.

## Driver behaviour

- **Integers.** `COUNT(*)` and `SUM()` return `bigint`, which `pg` would give as a string. A type parser turns `int8` into a JavaScript number, as mysql2 did with `supportBigNumbers` + `bigNumberStrings: false`. Values above 2^53 are not expected; XP totals are far below that.
- **Numerics.** `numeric` is parsed with `parseFloat`, like `decimalNumbers: true`.
- **Dates.** `date` is returned as its `'YYYY-MM-DD'` text, like `dateStrings: ['DATE']`.
- **Timestamps.** `timestamptz` comes back as a JS `Date`, like `DATETIME` with `timezone: 'Z'`.
- **JSON.** `jsonb` comes back parsed. The readers already accept both strings and objects.
- **Time zone.** Each new connection runs `SET TIME ZONE 'UTC'`.

## Supabase setup

1. Create a project at [supabase.com](https://supabase.com). Choose the region closest to the Render services.
2. **Extensions.** In Database → Extensions, enable `vector` and `citext`. The baseline migration also runs `CREATE EXTENSION IF NOT EXISTS` for both, which works for the default `postgres` user.
3. **Connection string.** In Connect → Connection string, choose the **Session pooler**. The URL looks like:
   ```
   postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```
   - Use the session pooler on port **5432**, not the transaction pooler on 6543. Migrations hold an advisory lock for a whole session, and the AI service uses prepared statements. Neither works in transaction mode.
   - The direct connection (`db.<ref>.supabase.co`) is IPv6 only, and Render does not reach IPv6 addresses.
4. **TLS.** Set `DB_SSL=true`. Supabase certificates chain to a public root, so `DB_SSL_CA` can stay empty. To pin it, download the CA from Database → Settings → SSL Configuration and put the PEM contents in `DB_SSL_CA`.
5. **Pool size.** The free tier allows a limited number of pooler clients. The web server, bot, AI service and archive job each open their own pool, so keep `DB_POOL_SIZE` at 5 or lower per Node service.

| `TEST_DB_*`, `E2E_DB_*` | MySQL | Postgres (CI uses `postgres` / `postgres` on `localhost:5432`) |

The AI service builds its SQLAlchemy URL from the same variables (`postgresql+asyncpg://…`), so nothing extra is needed for it.

## Cutover runbook

Because the database starts empty, the cutover is a configuration switch:

1. **Create** the Supabase project and copy the session-pooler URL (above).
2. **Point Render at it.** In Render → Environment Groups → `taskquest-database`:
   - Set `DB_URL` to the Supabase URL.
   - Set `DB_SSL=true`.
   - Clear `DB_SSL_CA`, unless you pinned the Supabase CA.
3. **Deploy.** Push the migration commits to `main`, or redeploy if already pushed. Render auto-deploys web, bot, AI and the archive job.
4. **Migrations run on start.** The first service to boot takes the advisory lock and runs `001_baseline`; the others wait and then see the schema is current. The AI service's build step indexes the help docs into `ai_embeddings`. On the very first deploy that build can run before any table exists; it then skips without failing. Once the web service is up, redeploy the AI service (or run `python -m app.rag.index_docs` in its shell) to index the docs.
5. **Players re-link.** Accounts are created again on the first bot command or web login. Progress from the TiDB database is not carried over.
6. **Retire TiDB** once you are satisfied. Keep a final `mysqldump` of it if you want an archive.

## Rollback

Redeploy the last MySQL-era commit and set `DB_URL` back to the TiDB URL. Nothing was copied out of TiDB, so it is exactly as it was. Anything written to Supabase in the meantime stays only in Supabase.

## Verification checklist

- [ ] `npm run db:migrate` on an empty database creates all tables; a second run says the schema is up to date.
- [ ] `npm test` with `TEST_DB_*` pointing at a throwaway Postgres runs the integration suites (shared, server, bot) and passes.
- [ ] `npm run test:e2e` passes.
- [ ] `pytest` in `apps/ai` passes (SQLite path), and so does `pytest tests/postgres` with `AI_TEST_DB_URL`.
- [ ] `npm run lint` and `npm run check` pass.
- [ ] Against Supabase:
  - log in on the web;
  - create, complete and edit a task;
  - claim a daily reward and a quest;
  - share a list and invite a party member;
  - ask the AI chat about your tasks (RAG);
  - run `npm run archive -- --days 365`.

## Behaviour differences to know about

- **Case-insensitive names.** Names that must be unique ignoring case (lists, templates, parties) use `citext`. Unlike MySQL's `utf8mb4_unicode_ci`, accents count: "Cafe" and "Café" can be two lists. Everything else compares exactly, as Postgres does. Task search uses `ILIKE`.
- **Vector search is exact.** There is no HNSW index: filtered to one user, an approximate index can return fewer than k rows. The exact scan over a user's few thousand chunks is fast. If it ever is not, add an HNSW index with `hnsw.iterative_scan` (pgvector 0.8+).
- **Timestamps keep milliseconds.** MySQL rounded most times to whole seconds; Postgres keeps what JavaScript sent, so elapsed-time checks (focus sessions, the daily claim window) are not off by a rounded second.
- **`updated_at`.** It changes only when a query sets it (see [SQL rewrite rules](#sql-rewrite-rules)).
- **`GREATEST` / `LEAST`.** In Postgres these ignore `NULL` arguments; MySQL returns `NULL`. The queries that use them either pass non-null values or wrap them in `COALESCE`.
- **Strict typing.** Postgres does not compare a string with a number implicitly. The code passes numbers for numeric columns, and the compatibility layer turns booleans into `1` / `0`.
- **Transactional DDL.** Each migration runs inside a transaction, so a failed migration leaves no half-applied schema.
- **Failed statements abort the transaction.** Postgres refuses every statement after an error until the transaction ends, so code that catches a duplicate key inside a transaction and retries (the import's list names, a re-assigned Discord handle) wraps the attempt in `savepoint()`.
- **No legacy upgrade path.** The MySQL-only `002_upgrade_legacy` migration and the MySQL collation risk it carried no longer apply.
